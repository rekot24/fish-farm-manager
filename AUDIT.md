## 1. What's already there and working well

- [x] **Layer 9 — Data model first.** `DetectResult`, `HealthStatus`, `Settings`, `DeviceConfig`, `TimerConfig`, `DetectorConfig`, `ProfileConfig` are all clean dataclasses defined before the logic that uses them. [`detection/result.py`](detection/result.py), [`bot/health_monitor.py`](bot/health_monitor.py), [`bot/config_manager.py`](bot/config_manager.py).
- [x] **Layer 10 — Interface before implementation.** Nearly every function has a docstring stating args/returns before the body; `capture/base.py` is a textbook example — an ABC with the three-method contract written out before any backend implements it.
- [x] **Layer 11 — Defensive programming.** Consistent existence checks, connection checks, and graceful fallbacks throughout — e.g. `HealthMonitor` caches last-known battery/temp so one failed ADB read doesn't wipe good data ([bot/health_monitor.py:88-90](bot/health_monitor.py#L88-L90)); `TemplateBank._load` raises clear, typed errors instead of returning garbage ([detection/template_bank.py:154-173](detection/template_bank.py#L154-L173)).
- [x] **Layer 8 — Code commenting.** Module-level docstrings explain purpose on every file; section headers use the dash-separator convention; non-obvious decisions are explained inline (e.g. the F-04 stale-worker fix in [bot/device_manager.py:127-140](bot/device_manager.py#L127-L140), the "no catch-all rule" note in [bot/state_rules.py:16-17](bot/state_rules.py#L16-L17)).
- [x] **Layer 1 — Settings store, mostly.** `config/settings.json` + `config_manager.Settings` is a real single source of truth: loads on startup with defaults for missing keys, live objects are swapped into workers via `DeviceManager.reload_settings()` / `reload_device_configs()` with no restart required ([bot/device_manager.py:242-257](bot/device_manager.py#L242-L257)).
- [x] **Layer 2 — Feature flags for timers.** `auto_farm_reset_enabled` and `end_run_reset_enabled` are checked at the top of every relevant function, every cycle, not cached at startup ([bot/device_worker.py:262](bot/device_worker.py#L262), [bot/device_worker.py:291](bot/device_worker.py#L291)) — this is exactly the pattern the standard asks for.
- [x] **Layer 5 — Status and visibility.** `DeviceManager.get_all_statuses()` always returns connection state, battery, temp, current state and last action, regardless of what's enabled — polled every 500ms by the UI ([bot/device_manager.py:178-216](bot/device_manager.py#L178-L216)).
- [x] **Layer 4 — Folder structure.** `bot/ config/ capture/ detection/ ui/ tools/ assets/` maps almost exactly to the standard's prescribed layout, and `tools/` genuinely holds reusable, app-agnostic utilities (`coordinate_finder.py`, `image_capture_tool.py`).
- [x] **Layer 6 — No silent failure.** No bare `except:` anywhere in the codebase (verified by grep) — every catch is typed or at minimum logs/returns a safe fallback.
- [x] **Layer 12 — Git as a thinking tool, partially.** Feature branches exist alongside `main` (`code-review-fixes-2026-08-27`, `portable-local-tooling-2026-08-27`), showing the branch-and-merge habit is in use.

## 2. What's missing entirely

- [x] **Layer 7 — Logging.** ~~There is no `logs/` directory, no `app.log`, no `errors.log`, no rotation, and no INFO/WARNING/ERROR/CRITICAL level distinction anywhere. All output goes to `print()` and an in-memory Tkinter log widget capped at 500 lines — closing the window loses the entire session history.~~ Added — [bot/app_logger.py](bot/app_logger.py) is the single unified log function every `_log()`/`log()` call site routes through: rotating `logs/app.log` filtered at `Settings.logging.level`, and `logs/errors.log` that always records ERROR/CRITICAL regardless of the enabled/level settings. Real levels assigned throughout `device_worker.py` and `device_manager.py` (not just plumbing — errors are ERROR, retries/degraded states are WARNING, normal flow is INFO). `LoggingConfig` is live-reloadable from the Settings dialog with no restart, same pattern as `HealthConfig`/`DebugConfig`. `logs/` added to `.gitignore`.
- [x] **README.md.** ~~No README exists anywhere in the repo (verified by search).~~ Added — describes what the app does and what each folder is responsible for.
- [ ] **Debug master switch + categories.** The standard's `debug.enabled` master toggle and per-category flags (`log_detections`, `log_actions`, `log_health`, `log_config_reads`, `screenshot_on_event`) don't exist. `DebugConfig` only has `save_failed_captures`, `log_state_changes`, `screenshot_dir` — there's no single switch that silences all debug output in production, and no central `_debug(category, msg)` function; log calls are ad hoc `self._log(...)` calls scattered through `device_worker.py`.
- [ ] **Dev vs. production error-handling mode.** The standard calls for a settings-driven switch between "fail loudly" (raise, surface) and "fail gracefully" (log + safest fallback). Today the app only has one mode: always graceful. `DeviceWorker._run()`'s top-level catch logs *every* exception, including unexpected ones, and never re-raises ([bot/device_worker.py:161-164](bot/device_worker.py#L161-L164)) — there's no way to make bugs surface loudly while developing.
- [ ] **Feature-flag profiles (the standard's meaning).** The standard's "Profile" is a saved snapshot of feature-flag states, restorable from the settings store. This app also uses the word "profile" (`lead_private.yaml` etc.), but those are static behavior/rule-set definitions loaded once at worker start — not live, not restorable snapshots of settings. The standard's actual profile-save/load feature doesn't exist here yet.
- [ ] **Automated tests.** No test files anywhere. Note: the standard itself flags this as a *future* layer, not yet mandatory ("On testing" section) — listed here for completeness, not as a violation.

## 3. What exists but needs to be refactored to match the standard

- [x] **UI calling worker internals directly.** ~~The standard's UI rule is non-negotiable: *"The UI never writes to workers directly. The UI never calls feature functions directly."* Two direct violations: `worker._execute_end_run()` called directly from the UI, and `self.manager._workers.get(serial)` reaching past `DeviceManager`'s public interface.~~ Fixed — added `DeviceManager.is_device_running(serial)` and `DeviceManager.trigger_end_run(serial)`, with a new `DeviceWorker.request_manual_end_run()` public entry point; the UI now only calls those. This also fixed a latent bug: the old direct call `worker._execute_end_run()` passed no `results` argument, but that method requires one — the manual "End Run" button was raising `TypeError` on every click. The fix reuses the same "expire the timer so it fires with fresh results on the next scan" mechanism the lead's `force_end_run` event already used correctly.
- [ ] **Behavior flags trapped in static profile YAML.** `revive_enabled`, `disable_auto_on_death`, `save_screenshot`, `cascade_reset_on_end_run.enabled`, `eaten_by_detection.enabled` all live in `config/profiles/*.yaml` under `behaviors`, loaded once when a worker starts and never re-read. This contradicts the Layer 1 rule ("every feature checks its own enabled flag on every run, not once at startup") and Layer 2 ("no restart required"). These read like true feature flags, not rule-set structure — worth moving into `DeviceConfig`/`Settings` so toggling them is live, and reserving YAML profiles purely for the state-detection rule sets they're built for.
- [ ] **`config_manager.py` bundles three responsibilities.** It owns settings *and* device config *and* profile loading *and* validation in one 392-line file. Layer 4's rule is explicit: "if a file does more than one thing, it should be two files." The standard's own suggested convention (`settings_schema.py` / `settings_store.py` split) points at splitting this into `settings.py`, `devices.py`, `profiles.py` under `config/`.
- [ ] **Raw `print()` calls outside the log path.** A handful of `print()` calls bypass the logging path entirely: [bot/config_manager.py:155](bot/config_manager.py#L155), [bot/config_manager.py:229](bot/config_manager.py#L229), [bot/config_manager.py:351](bot/config_manager.py#L351), and [ui/app.py:178](ui/app.py#L178) (a resize-debug print left in). Layer 3's rule is explicit: no raw print statements for debugging — once the debug layer exists, these should route through it (or through the manager's log function, for the `config_manager.py` cases, which currently have no access to a logger at all since they're free functions).
- [ ] **Git commit message style.** Recent messages (`"fixing erros on startup"`, `"pass1 fixes"`, `"image capture and mgmt added"`) don't follow the standard's `type: what changed and why` convention (e.g. `fix: ADB reconnect no longer blocks the main loop`). Not urgent, but worth adopting going forward per Layer 12.
- [ ] **Health checks run as blocking subprocess calls inside the scan loop.** Not an explicit standard rule, but relevant to Layer 6/11: `HealthMonitor.check()` runs three separate `adb` subprocess calls synchronously every iteration ([bot/health_monitor.py:76-79](bot/health_monitor.py#L76-L79)), each with its own timeout — worth a look once the logging layer exists, since a slow/hung ADB call is currently invisible (no log line records how long a health check took).

## 4. Addendum — "No magic numbers" (rule not yet published in `app-framework.md`, checked ahead of the doc update)

You flagged this rule verbally: *no raw numeric literal sits in the middle of code unexplained — if a number means something, it gets a name.* It isn't in the fetched copy of `app-framework.md` yet, but the codebase was scanned against it. Verdict: **inconsistently applied** — a few places already do this correctly, but timeouts, retry delays, and layout math are overwhelmingly raw literals, often the *same* literal copy-pasted across many files.

**Already done right** (for contrast — these are the pattern to copy elsewhere):
- [x] `capture/scrcpy_socket.py:74-75` — `_HEADER_SIZE = 64`, `_VIDEO_HEADER_SIZE = 12` are named class constants with comments.
- [x] `capture/scrcpy_socket.py:52` — `_BASE_PORT = 27183` is named (though the `% 100` range size two lines below it, at [scrcpy_socket.py:61](capture/scrcpy_socket.py#L61), is not).
- [x] `ui/app.py:33-34` — `POLL_INTERVAL_MS`, `LOG_MAX_LINES` are named class constants.
- [x] Health thresholds (`battery_min_percent`, `temp_pause_celsius`, etc.) already live in `HealthConfig` — the dataclass field *is* the name. This is the model to extend the rest of the timing values to.

**Needs a name:**

- [ ] **The same ADB timeout literal, duplicated independently 8+ times.** `10.0` / `10` appears as an unexplained subprocess timeout in [bot/device_manager.py:62](bot/device_manager.py#L62), [bot/actions.py:20](bot/actions.py#L20) (default), [bot/health_monitor.py:207](bot/health_monitor.py#L207), [ui/add_device_dialog.py:95](ui/add_device_dialog.py#L95), [tools/coordinate_finder.py:115](tools/coordinate_finder.py#L115), [tools/image_capture_tool.py:336,948](tools/image_capture_tool.py#L336) — plus sibling values `5.0`/`5`, `15.0`, `8.0` for the same *kind* of call scattered elsewhere ([bot/health_monitor.py:115,139](bot/health_monitor.py#L115), [bot/actions.py:117,158,173,189](bot/actions.py#L117), [capture/adb_screencap.py:34](capture/adb_screencap.py#L34)). None of these share a constant — tuning "how patient are we with a slow ADB call" today means hunting through six-plus files.
- [ ] **Device recovery/settle delays in `device_worker.py`, all unnamed.** `_stop_event.wait(timeout=3.0)` after force-stop before relaunch ([device_worker.py:490](bot/device_worker.py#L490)), `timeout=1.0` before sleep during battery shutdown ([device_worker.py:588](bot/device_worker.py#L588)), `timeout=60.0` battery-sleep poll interval ([device_worker.py:592](bot/device_worker.py#L592)), `timeout=10.0` after wake before relaunch ([device_worker.py:599](bot/device_worker.py#L599)), `timeout=30.0` temp-pause poll interval ([device_worker.py:611](bot/device_worker.py#L611)), plus `join(timeout=5.0)` on worker shutdown ([device_worker.py:130](bot/device_worker.py#L130)). Each one encodes a real operational decision ("how long does this device need to settle") with no comment or name — exactly the class of value `HealthConfig` already got right for battery/temp thresholds.
- [ ] **`_max_unknown_s = 60.0`** ([device_worker.py:98](bot/device_worker.py#L98)) — the crash-detection timeout. It's assigned to a named attribute, which is halfway there, but the value itself is a bare literal set in `__init__` with no comment on why 60s, and it isn't reachable from `Settings`/`HealthConfig` the way the other health tuning values are.
- [ ] **`target_s *= 2.0`** ([device_worker.py:170](bot/device_worker.py#L170)) — doubles the scan interval under thermal throttle. The multiplier itself has no name or explanation for why 2x specifically.
- [ ] **`sleep_s = max(0.05, ...)`** ([device_worker.py:171](bot/device_worker.py#L171)) — the floor on loop sleep time (50ms) is unexplained.
- [ ] **Duplicated template-confidence default.** `0.82` is hardcoded as the parameter default in *four separate functions* in [detection/detector.py](detection/detector.py#L31) (lines 31, 101, 144, 169), in addition to already being named once as `Settings.template_confidence_default` in [bot/config_manager.py:73](bot/config_manager.py#L73). These should reference the one named value instead of retyping the number four more times — right now, changing the default confidence means editing five places and hoping none get missed.
- [ ] **UI resize math in `_resize_to_fit`** ([ui/app.py:170-179](ui/app.py#L170-L179)) — `min(device_count, 10)` (device display cap), `capped * 78` (assumed pixel height per device row), `log_height = 220`, `top_height = 60` are all bare literals encoding real layout assumptions. `78` in particular is fragile: it silently goes stale the moment `DevicePanel`'s actual rendered height changes, with nothing tying the two together.
- [ ] **`bot/health_monitor.py` temperature parsing heuristics** — `if raw > 1000` (millidegrees-vs-degrees heuristic, [line 185](bot/health_monitor.py#L185)) and `0 < temp_c < 120` (sanity bounds, [line 191](bot/health_monitor.py#L191)) are both explained in comments but not lifted into named constants.
- [ ] **Minutes-to-seconds conversions.** `* 60` appears unnamed in four places converting configured minute intervals to seconds ([bot/device_worker.py:265,294](bot/device_worker.py#L265), [bot/device_manager.py:225-226](bot/device_manager.py#L225-L226)). Low risk since `* 60` reads as obviously "minutes to seconds," but worth a `SECONDS_PER_MINUTE` constant or at least a comment for strict compliance.
- [ ] **Misc retry/backoff sleeps in `capture/scrcpy_socket.py`** — `time.sleep(0.5)` ([line 144](capture/scrcpy_socket.py#L144)) and `time.sleep(0.2)` ([line 306](capture/scrcpy_socket.py#L306), has a same-line comment but no name) are unnamed retry delays.
