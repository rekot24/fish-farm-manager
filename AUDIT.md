# Standards Audit — Be Fish Farm Manager

Audited against [`app-framework.md`](https://github.com/Rekot24/dev-standards/blob/main/app-framework.md) (dev-standards repo, updated Sept 2026).

Scope: everything under the repo root except `.venv/`. No code was changed for this audit — this is a read-only assessment. Check items off as you close them; re-run the audit skill (or ask me) periodically to keep this current.

## 1. What's already there and working well

- [x] **Layer 9 — Data model first.** `DetectResult`, `HealthStatus`, `Settings`, `DeviceConfig`, `TimerConfig`, `DetectorConfig`, `ProfileConfig` are all clean dataclasses defined before the logic that uses them. [`detection/result.py`](detection/result.py), [`bot/health_monitor.py`](bot/health_monitor.py), [`config/settings.py`](config/settings.py), [`config/devices.py`](config/devices.py), [`config/profiles.py`](config/profiles.py).
- [x] **Layer 10 — Interface before implementation.** Nearly every function has a docstring stating args/returns before the body; `capture/base.py` is a textbook example — an ABC with the three-method contract written out before any backend implements it.
- [x] **Layer 11 — Defensive programming.** Consistent existence checks, connection checks, and graceful fallbacks throughout — e.g. `HealthMonitor` caches last-known battery/temp so one failed ADB read doesn't wipe good data ([bot/health_monitor.py:88-90](bot/health_monitor.py#L88-L90)); `TemplateBank._load` raises clear, typed errors instead of returning garbage ([detection/template_bank.py:154-173](detection/template_bank.py#L154-L173)).
- [x] **Layer 8 — Code commenting.** Module-level docstrings explain purpose on every file; section headers use the dash-separator convention; non-obvious decisions are explained inline (e.g. the F-04 stale-worker fix in [bot/device_manager.py:127-140](bot/device_manager.py#L127-L140), the "no catch-all rule" note in [bot/state_rules.py:16-17](bot/state_rules.py#L16-L17)).
- [x] **Layer 1 — Settings store, mostly.** `config/settings.json` + `config.settings.Settings` is a real single source of truth: loads on startup with defaults for missing keys, live objects are swapped into workers via `DeviceManager.reload_settings()` / `reload_device_configs()` with no restart required ([bot/device_manager.py:242-257](bot/device_manager.py#L242-L257)).
- [x] **Layer 2 — Feature flags for timers.** `auto_farm_reset_enabled` and `end_run_reset_enabled` are checked at the top of every relevant function, every cycle, not cached at startup ([bot/device_worker.py:262](bot/device_worker.py#L262), [bot/device_worker.py:291](bot/device_worker.py#L291)) — this is exactly the pattern the standard asks for.
- [x] **Layer 5 — Status and visibility.** `DeviceManager.get_all_statuses()` always returns connection state, battery, temp, current state and last action, regardless of what's enabled — polled every 500ms by the UI ([bot/device_manager.py:178-216](bot/device_manager.py#L178-L216)).
- [x] **Layer 4 — Folder structure.** `bot/ config/ capture/ detection/ ui/ tools/ assets/` maps almost exactly to the standard's prescribed layout, and `tools/` genuinely holds reusable, app-agnostic utilities (`coordinate_finder.py`, `image_capture_tool.py`).
- [x] **Layer 6 — No silent failure.** No bare `except:` anywhere in the codebase (verified by grep) — every catch is typed or at minimum logs/returns a safe fallback.
- [x] **Layer 12 — Git as a thinking tool, partially.** Feature branches exist alongside `main` (`code-review-fixes-2026-08-27`, `portable-local-tooling-2026-08-27`), showing the branch-and-merge habit is in use.

## 2. What's missing entirely

- [x] **Layer 7 — Logging.** ~~There is no `logs/` directory, no `app.log`, no `errors.log`, no rotation, and no INFO/WARNING/ERROR/CRITICAL level distinction anywhere. All output goes to `print()` and an in-memory Tkinter log widget capped at 500 lines — closing the window loses the entire session history.~~ Added — [bot/app_logger.py](bot/app_logger.py) is the single unified log function every `_log()`/`log()` call site routes through: rotating `logs/app.log` filtered at `Settings.logging.level`, and `logs/errors.log` that always records ERROR/CRITICAL regardless of the enabled/level settings. Real levels assigned throughout `device_worker.py` and `device_manager.py` (not just plumbing — errors are ERROR, retries/degraded states are WARNING, normal flow is INFO). `LoggingConfig` is live-reloadable from the Settings dialog with no restart, same pattern as `HealthConfig`/`DebugConfig`. `logs/` added to `.gitignore`.
- [x] **README.md.** ~~No README exists anywhere in the repo (verified by search).~~ Added — describes what the app does and what each folder is responsible for.
- [x] **Debug master switch + categories.** ~~The standard's `debug.enabled` master toggle and per-category flags don't exist... there's no single switch that silences all debug output in production, and no central `_debug(category, msg)` function.~~ Fixed — `DebugConfig` now has `enabled` (master, default `False`) plus `log_detections`, `log_actions`, `log_health`, `log_config_reads`, `screenshot_on_event` alongside the pre-existing `log_state_changes`. Central `debug()` function lives in [bot/app_logger.py](bot/app_logger.py), with a thin `_debug(category, msg)` wrapper on both `DeviceWorker` and `DeviceManager` delegating to it through their existing `_log()`. Deliberately additive, not a replacement: every debug category supplements the always-on INFO/WARNING/ERROR logs from Phase 1 with extra opt-in detail (detector scores every scan, raw health values every scan, action-dispatch tracing, config-reload tracing) — turning debug off never makes an existing log line disappear. All exposed as checkboxes in the Settings dialog.
- [x] **Bonus fix found while wiring the Settings dialog's new checkboxes: silent settings reset on Save.** `SettingsDialog._save()` constructed fresh `HealthConfig(...)`/`DebugConfig(...)`/`LoggingConfig(...)` objects from only the fields the dialog exposes — every field added in Phase 3 that the dialog doesn't have a row for (`HealthConfig`'s settle/poll delays, all of `AdbConfig`) would silently reset to its dataclass default the moment anyone clicked Save, discarding whatever was actually loaded from `settings.json`. Fixed with `dataclasses.replace()` off the original loaded `Settings` object instead of constructing fresh ones — confirmed with a real-Tkinter test that customized, dialog-unexposed field values survive a save untouched.
- [ ] **`DebugConfig.save_failed_captures` exists and is exposed in the UI, but is never read anywhere.** Noticed while auditing the Debug section for this phase — grep confirms it's only ever written (loaded/saved/UI-bound), never checked by any capture/detection code path. Not fixed here — it's a different gap (a flag that does nothing) from what this phase was scoped to, and belongs with a specific capture-failure-handling feature, not the debug-layer plumbing itself.
- [x] **Dev vs. production error-handling mode.** ~~The standard calls for a settings-driven switch between "fail loudly" (raise, surface) and "fail gracefully" (log + safest fallback). Today the app only has one mode: always graceful.~~ Fixed — `Settings.development_mode: bool` (default `False`), and `DeviceWorker._run()`'s top-level catch now logs unconditionally (a record must exist regardless of mode) then re-raises only when `development_mode` is `True`. Deliberately scoped to outermost-boundary catches only, not every `except Exception` in the codebase — the standard's own example distinguishes named/expected failures (always graceful) from the genuinely-unexpected bucket at the top level (mode-dependent); most of this app's broad catches are the first kind and correctly stay untouched. `capture/scrcpy_socket.py`'s `_decode_loop()` got the same treatment (it's the same category: an outermost catch-all for its own background thread), which required threading `development_mode` through `make_backend()` into both capture backends. Verified by actually forcing exceptions at runtime in a background thread and observing the two behaviors — not just checking config values — for both `DeviceWorker._run()` and `_decode_loop()`.
- [x] **Feature-flag profiles (the standard's meaning).** ~~The standard's "Profile" is a saved snapshot of feature-flag states, restorable from the settings store. This app also uses the word "profile" (`lead_private.yaml` etc.), but those are static behavior/rule-set definitions loaded once at worker start — not live, not restorable snapshots of settings. The standard's actual profile-save/load feature doesn't exist here yet.~~ Fixed (data layer only — see ROADMAP Phase 8) — named `BehaviorPreset` in code, deliberately not "profile," to avoid the exact collision this bullet describes; CLAUDE.md's very first session log had already anticipated needing this distinction before the split was identified. Snapshots `TimerConfig` + `DeathBehaviorConfig` only (the live, per-cycle-checked flags Phase 3/6 established) — `DeviceConfig.role` is excluded by design, confirmed safe by tracing every role-gated decision in the bot loop first (role lives in the *consuming* code, never in the snapshotted fields). `config/presets.py` + `config/behavior_presets.json`, save/load/delete/list/apply, all via `dataclasses.replace()` so applying a preset touches only `timers`/`death_behavior` on the target device. No presets shipped by default; the actual Save-as/Load UI is Phase 11's job, which already listed this phase as its prerequisite.
- [ ] **Automated tests.** No test files anywhere. Note: the standard itself flags this as a *future* layer, not yet mandatory ("On testing" section) — listed here for completeness, not as a violation.

## 3. What exists but needs to be refactored to match the standard

- [x] **UI calling worker internals directly.** ~~The standard's UI rule is non-negotiable: *"The UI never writes to workers directly. The UI never calls feature functions directly."* Two direct violations: `worker._execute_end_run()` called directly from the UI, and `self.manager._workers.get(serial)` reaching past `DeviceManager`'s public interface.~~ Fixed — added `DeviceManager.is_device_running(serial)` and `DeviceManager.trigger_end_run(serial)`, with a new `DeviceWorker.request_manual_end_run()` public entry point; the UI now only calls those. This also fixed a latent bug: the old direct call `worker._execute_end_run()` passed no `results` argument, but that method requires one — the manual "End Run" button was raising `TypeError` on every click. The fix reuses the same "expire the timer so it fires with fresh results on the next scan" mechanism the lead's `force_end_run` event already used correctly.
- [x] **Behavior flags trapped in static profile YAML.** ~~`revive_enabled`, `disable_auto_on_death`, `save_screenshot`, `cascade_reset_on_end_run.enabled`, `eaten_by_detection.enabled` all live in `config/profiles/*.yaml` under `behaviors`, loaded once when a worker starts and never re-read.~~ Fixed — and a fresh trace of every actual read of `profile.behaviors` before touching anything turned up more than the audit had listed: **most of the `behaviors:` block was already dead code.** `auto_farm_reset`/`end_run_reset` were stale duplicates of `TimerConfig` (never consulted — the code already read `self.cfg.timers.*`); `rejoin_on_kick`, `rejoin_source`, `auto_rejoin` (support profiles), `cascade_reset_on_lead_reset` (support_private), and `move_to_private_on_revive_exhausted` (lead_public) were never read by any code path at all, in any profile. Only `cascade_reset_on_end_run`, `eaten_by_detection`, and `dead_state` were real.
  Those three moved to live `config/devices.py` fields: two new fields on `TimerConfig` (`cascade_reset_enabled`, `cascade_reset_delay_after_lead_s` — grouped there since it's the same "reset cycle" concept the existing timer fields cover, and the code reading it already lives in `device_worker.py`'s "Timer logic" section, not death-handling), and a new `DeathBehaviorConfig` on `DeviceConfig` for the other five. `load_devices()` computes profile-aware fallback defaults for entries missing these fields (e.g. `eaten_by_detection_enabled` defaults to `is_lead`, matching every profile's old value exactly) — verified against all 6 real configured devices, no edits made to the actual `devices.json`.
  Consequence: the `behaviors:` block is now empty in every profile, so it's removed from all four YAML files and from `ProfileConfig` itself — profiles are purely state-detection rule-set metadata now (`profile_name`/`role`/`server_type`/`status`/`detectors_required`), which is what Layer 4 modularity actually wants them for.
  Found and fixed in passing: `ui/device_settings_dialog.py` had the identical "constructs a fresh config object from only its exposed fields" bug as `ui/settings_dialog.py` (AUDIT §2) — fixed with the same `dataclasses.replace()` pattern before the new fields could be silently reset by it.
- [x] **`config_manager.py` bundles three responsibilities.** ~~It owns settings *and* device config *and* profile loading *and* validation in one 392-line file. Layer 4's rule is explicit: "if a file does more than one thing, it should be two files."~~ Fixed — split into [config/settings.py](config/settings.py), [config/devices.py](config/devices.py), and [config/profiles.py](config/profiles.py) (load-only — profiles are edited by hand, not through the UI), sharing path resolution from a new [config/paths.py](config/paths.py) rather than each duplicating the same five one-line functions. `bot/config_manager.py` deleted outright (no shim) and all 10 importing files repointed. Verified with an import-chain + functional round-trip smoke test (load_settings/load_devices/load_profile against the real config files).
- [x] **Raw `print()` calls outside the log path.** ~~A handful of `print()` calls bypass the logging path entirely: config/settings.py, config/devices.py, config/profiles.py, and a resize-debug print left in ui/app.py.~~ Fixed, and the scope grew once a fresh repo-wide grep was run for this phase: 20 more `print()` calls turned up in `capture/scrcpy_socket.py` and `capture/adb_screencap.py` that were never in the original list, plus one in `main.py`'s config-load failure path. All now route through `app_logger.log()` directly (the three `config/*.py` free functions and the two capture backends have no natural `log_fn`/instance to call through, so they call the module-level function itself, same as any other caller). `ui/app.py`'s resize-debug print was deleted outright rather than given a new debug category, per the option the roadmap already offered. Fixing this required breaking a circular import (`config/settings.py` → `bot/app_logger` → `config/settings.py`) by moving `app_logger.py`'s `LoggingConfig`/`DebugConfig` imports behind `TYPE_CHECKING` — confirmed safe since neither is ever constructed or isinstance-checked, only attribute-read. Verified with a full-repo compile pass and a functional test confirming the standalone `config.settings` import path (the harder circularity direction) works, plus the missing-`settings.json` WARNING path actually fires through the fallback print (correctly scoped to patch the name bound inside `config.settings`'s own namespace, not the origin module — an easy mistake the first test attempt made).
  Remaining, deliberately unfixed: `bot/device_manager.py`'s and `bot/device_worker.py`'s `_default_log_fn` fallbacks, and `app_logger.log()`'s own pre-configuration print — these three *are* the routing mechanism, or exist specifically for the case where there's nothing else to route through yet, not something that should route through itself.
- [ ] **Git commit message style.** Recent messages (`"fixing erros on startup"`, `"pass1 fixes"`, `"image capture and mgmt added"`) don't follow the standard's `type: what changed and why` convention (e.g. `fix: ADB reconnect no longer blocks the main loop`). Not urgent, but worth adopting going forward per Layer 12.
- [ ] **Health checks run as blocking subprocess calls inside the scan loop.** Not an explicit standard rule, but relevant to Layer 6/11: `HealthMonitor.check()` runs three separate `adb` subprocess calls synchronously every iteration ([bot/health_monitor.py:76-79](bot/health_monitor.py#L76-L79)), each with its own timeout — worth a look once the logging layer exists, since a slow/hung ADB call is currently invisible (no log line records how long a health check took).

## 4. Addendum — "No magic numbers" (rule not yet published in `app-framework.md`, checked ahead of the doc update)

You flagged this rule verbally: *no raw numeric literal sits in the middle of code unexplained — if a number means something, it gets a name.* It isn't in the fetched copy of `app-framework.md` yet, but the codebase was scanned against it. Verdict: **inconsistently applied** — a few places already do this correctly, but timeouts, retry delays, and layout math are overwhelmingly raw literals, often the *same* literal copy-pasted across many files.

**Already done right** (for contrast — these are the pattern to copy elsewhere):
- [x] `capture/scrcpy_socket.py:74-75` — `_HEADER_SIZE = 64`, `_VIDEO_HEADER_SIZE = 12` are named class constants with comments.
- [x] `capture/scrcpy_socket.py:52` — `_BASE_PORT = 27183` is named (though the `% 100` range size two lines below it, at [scrcpy_socket.py:61](capture/scrcpy_socket.py#L61), is not).
- [x] `ui/app.py:33-34` — `POLL_INTERVAL_MS`, `LOG_MAX_LINES` are named class constants.
- [x] Health thresholds (`battery_min_percent`, `temp_pause_celsius`, etc.) already live in `HealthConfig` — the dataclass field *is* the name. This is the model to extend the rest of the timing values to.

**Needs a name — all fixed in ROADMAP.md Phase 3:**

- [x] **The same ADB timeout literal, duplicated independently 8+ times.** ~~`10.0` / `10` appears as an unexplained subprocess timeout in bot/device_manager.py, bot/actions.py, bot/health_monitor.py, ui/add_device_dialog.py, tools/coordinate_finder.py, tools/image_capture_tool.py — plus sibling values `5.0`/`5`, `15.0`, `8.0` for the same kind of call scattered elsewhere.~~ Fixed — six named, tagged constants in [config/constants.py](config/constants.py) (`ADB_QUICK_TIMEOUT_S`, `ADB_DEFAULT_TIMEOUT_S`, `ADB_LAUNCH_TIMEOUT_S`, `ADB_SCREENCAP_TIMEOUT_S`, `ADB_SCREENCAP_BATCH_TIMEOUT_S`, `ADB_RECONNECT_SETTLE_S` — kept as three-plus distinct tiers rather than collapsed to one value, since they genuinely tolerate different latency). Live-wired into a new `AdbConfig` on `Settings` for call sites that already hold a live settings reference (`HealthMonitor`, `DeviceManager`); used as static named defaults (not yet settings-store-threaded) in `bot/actions.py`'s free functions and the three standalone Tkinter tool dialogs, since threading a live `Settings` reference through those would be a materially bigger change than naming a constant — noted as a deliberate scope boundary, not silently dropped.
- [x] **Device recovery/settle delays in `device_worker.py`, all unnamed.** ~~`_stop_event.wait(timeout=3.0)` after force-stop before relaunch, `timeout=1.0` before sleep during battery shutdown, `timeout=60.0` battery-sleep poll interval, `timeout=10.0` after wake before relaunch, `timeout=30.0` temp-pause poll interval, plus `join(timeout=5.0)` on worker shutdown.~~ Fixed — the five settle/poll values are now live fields on `HealthConfig` (`crash_recovery_settle_s`, `battery_sleep_settle_s`, `battery_sleep_poll_s`, `wake_settle_s`, `temp_pause_poll_s`), read directly from `self.settings.health.*` at each use site (not cached, so a live settings change takes effect immediately). - [x] **Duplicated template-confidence default.** ~~`0.82` hardcoded as the parameter default in four separate functions in detection/detector.py, in addition to already being named once as `Settings.template_confidence_default`.~~ Fixed — all five now reference the single `DEFAULT_TEMPLATE_CONFIDENCE` constant in `config/constants.py`; verified via `inspect.signature` in the Phase 3 smoke test that `detector.py`'s default and `Settings.template_confidence_default`'s default are the same object.
